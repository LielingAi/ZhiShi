# 经验反喂效果评估（1.1.3 任务 2）

> 要回答的问题：**研究做得越多，下一次是否真的更快？**
> 蒸馏弧（research_events → 按域蒸馏 → 逐 turn 反喂）已闭环，但从未量化。本文定义度量口径、数据要求与判定标准；数据达标后执行评估并回写结论。

## 一、度量指标

| 指标 | 定义 | 为什么用它 |
|---|---|---|
| **重复踩坑率** | 同域任务序列中，「同一命令串 + 非零 exit」重复出现的次数 / 命令失败总次数 | 蒸馏弧的核心承诺是「死路不重蹈」——重复踩坑率是它的直接体检指标 |
| **平均回合数** | 同域任务完成（或放弃）所需的 loop 回合数 | 反喂有效应该表现为「更快收敛」，回合数是收敛速度的代理 |
| **任务时长** | 同域任务的 wall-clock 时长 | 辅助指标；受环境/网络影响大，只做参考不作判定 |
| **反喂注入量** | 每 turn system prompt 中蒸馏反喂段的字节数 | 过程指标：确认反喂真的发生了（不是空注入），并观察注入长度与效果的粗关系 |

**不用的指标**：蒸馏产物「被引用」次数——LLM 内部引用无法可靠观测，不用它做判定。

## 二、数据要求

- 按 `task_kind` 分组（binary / pentest / whitebox / ai-security），**经验不跨域混压，评估也分域做**。
- 每域需要 **≥ 10 组可比任务**：同一 bug_class 或相似目标形态（如 binary 域的 stack-overflow 序列），且时间上跨越至少一次蒸馏周期（6h），否则「反喂前后」无对比意义。
- 提取口径：从 loop 会话文件（`~/.zhishi/loop-sessions/*.jsonl`，每行一条消息，`toolResult` 行带 exit 信息）提取命令执行序列；research_events 提供任务边界与结果。

## 三、判定标准

- **有效**：反喂启用后，同域重复踩坑率下降 **≥ 30%**，或平均回合数下降且成功率（success 事件占比）不降。
- **无效/需调参**：重复踩坑率无明显变化——按顺序检查：(1) 蒸馏产物是否真的注入（反喂注入量）；(2) 蒸馏质量（产物是否只是事件复读而非提炼）；(3) 蒸馏周期/注入长度。
- **维持现状**：数据无显著差异但产物质量主观可接受——记录后下轮数据再评。

## 五、执行方式

数据达标后：
1. 跑提取脚本（从 loop-sessions 提取命令序列与 exit，按 task_kind/时间窗分组）
2. 对照 research_events 划分「反喂前/后」样本
3. 按第三节判定，回写本文档「当前状态」节并附数据表
