# 1.2.7 设计 —— 上下文管理与压缩

> 版本主题：上下文管理——系统提示与会话历史的全生命周期（增长、预算、压缩、存活）。
> 方向：做深不做广，不做新功能。
> 用户拍板（2026-08-20）：①切分按「研究阶段」；②域判定 = 配方默认 + 内容信号动态修正；③窗口口径按 preset 声明值（deepseek 1M）；④一版全量做完，不分期。

## 一、摸底结论（实证，设计前提）

系统提示侧（实测，security 场景）：
- 全量 append ≈ 14.4K 字符（≈3.6K tok @ chars/4），其中 **skills 段独占 ~11K（77%）**——12 个 bundled skills 无条件全量注入（`skills.ts:121-132` 无域过滤入参），是系统提示的第一大头。
- 能力清单段硬顶 4000，**全量列出所有配方与具名环境**，不按当前域收窄。
- 域（domain.json）目前只在两处生效：研究记忆分域过滤（1.2.4）+ TUI 信号卡；工具/skills/subagents/能力清单全不分域。

历史侧：
- jsonl 全量持久化（语义不动）；thinking 块原样留历史（占比曾实测 43%）；toolResult 有 head/tail 15KB 截流（env-exec）。
- 压缩（compaction.ts）挂载 transformContext，阈值 contextWindow×0.8，纯裁剪不生成摘要。

压缩三缺陷（1.2.6 边界包后仍存）：
1. **第一档空转**：keep 集 = 任务锚 ∪ 关键消息 ∪ 最近 4 轮，关键消息命中率过高（实测 ~52%）时并集逼近全集，裁完仍超阈值直接掉第二档。
2. **usage 锚定使裁后重估失效**：`estimateContextTokens` 找到保留的旧 assistant 的 API 实测 usage（压缩前全量值）+ 尾部估算，裁掉的量被 usage 锚加回来——裁后重估失真，第二档判定不可靠。
3. **存活契约两头漏**：中文突破语义（拿到 shell/权限提升/复现成功）不收；exit=0 的约束事实（「路径不可写」「端口关闭」类排除性结论）不收；fuzz 崩溃信号（SIGSEGV/ASAN/core dumped）不收——而这些正是安全研究的死路与突破口。

pi Hook 面（node_modules 实证）：
- `transformContext`：每次 LLM 调用前跑（无跳过路径），返回值只替换当次请求视图，**不污染 transcript**——实时管理主挂载点。契约要求不 throw。
- `prepareNextTurn`：能真回写上下文（1.2.7 暂不用，保留为后续口子）。
- pi 自带完整 compaction 摘要管线（shouldCompact/prepareCompaction/compact/generateSummary + 结构化 SUMMARIZATION_PROMPT），但**全是库函数，未接 agentLoop**——触发责任在宿主。
- **溢出兜底**：agentLoop 无任何自动压缩重试；`isContextOverflow`（pi-ai utils）提供检测（26 条 provider 错误正则 + 静默溢出 + length 截断），宿主必须自研「检测 → 压缩 → 重试」。

窗口口径：
- 1.2.7 前：pi loop 恒按 `?? 200_000` 兜底，preset 声明的 1M（deepseek-v4-pro/flash）传不进 loop——压缩阈值系统性偏低 5 倍。
- 已接线：`resolveLoopModel` / `resolveLoopModelFromEnv` 经 `lookupModelContextLength`（registry：custom > discovered > preset > litellm）取真实窗口；未知模型才落 200K 兜底。

**1M 口径的推论**：压缩从「常态生存机制」变「稀有事件」；实时管理的重心从「活着」转向**布局与组织**——上下文里有什么、模型能不能找对地方。

## 二、架构：离线管理（已有）+ 实时管理（新建）

- **离线管理**（已有，不动）：jsonl 全量存档、认知/安全蒸馏弧、专家知识库。
- **实时管理**（本版新建）：每次 LLM 调用前，对当前会话上下文做 **切分 → 标注 → 采样锚定 → 注意力布局**，输出当次请求的上下文视图。

### 2.1 切分（segmentation）——按研究阶段

切分单位 = **段（segment）**：以 user 消息为 turn 边界，一条 user 起到下一条 user 前为一段。每段推断研究阶段（phase），对照通用研究循环：

| phase | 含义 | 推断信号（段内 toolCall 名 + 命令/正文关键词，确定性启发式，无 LLM） |
|---|---|---|
| `anchor` | 任务锚 | 首条 user 所在段，恒定 |
| `recon` | 侦察 | nmap/masscan/扫描/枚举/garak/子域名/指纹 |
| `analysis` | 分析 | grep/审计/反汇编/readelf/IDA 类/数据流/污点 |
| `construction` | 构造 | 写 exp/PoC/脚本/payload 构造 |
| `execution` | 执行 | exploit 运行/拿 shell/会话开启/fuzz 起跑 |
| `evaluation` | 评估 | 验证/复测/flag 命中/结论判定 |

规则：段内信号打分取最高；**无信号继承上一段 phase**（研究阶段有粘性，连续工具调用属同一阶段）；首段恒为 anchor。

### 2.2 标注（annotation）

每段携带：phase、token 估算（chars/4 同口径）、key 命中行（扩展后的存活契约，见 2.4）、距末尾 turn 数（age）、域标签（见三）。标注是纯数据，不进上下文——进上下文的是布局产物。

### 2.3 采样锚定（sampling-anchored budget）

超阈值时不走固定档位，按分段构成**采样锚定压缩比例**：

1. 必保全量：anchor 段 ∪ 当前阶段（末尾 phase）所有段 ∪ key 段（段内命中存活契约）。
2. 可压缩集 = 历史阶段的非 key 段，从最老的开始。
3. 需要削减量 Δ = 估算 tokens − 目标（threshold）；按段体量从最老段起**逐个 stub 化**直到 Δ 达标——压缩比例由内容构成锚定，不是预设档位。
4. 仍不达标（key 段本身超阈值）→ 对保留段做逐条正文截断（沿用 1.2.6 第二档 b），最终仍超 → 明确日志引导 /reset。

### 2.4 存活契约扩展（修「两头漏」）

`KEY_MESSAGE_PATTERNS` 扩三族（保持保守，宁多勿缺）：
- 中文突破/约束：`拿到shell|权限提升|提权成功|复现成功|利用成功|突破口|约束|不可写|不存在|拒绝访问` 等；
- exit=0 约束事实：`exit=0` 且同文本含排除性结论词（不可写/不存在/关闭/denied/not found/unavailable）；
- fuzz 崩溃信号：`SIGSEGV|SIGABRT|SIGILL|SIGFPE|AddressSanitizer|ASAN|core dumped|crash`（与 binary 域 signals 对齐）。

error 信号维持 1.2.6 的收窄语义（良性搭配剥离后再判）。

### 2.5 注意力布局（attention layout）

LLM 注意力「去中间」——重点不是内容多，而是**知道内容在哪里、且关键信息在手**。布局产物：

```
[头] anchor 段原文（任务锚）
[中] 历史阶段 stub 索引序列——每段一条矮 stub：
     「[段#i recon 已压缩] 关键信息：<命中行摘录>; 工具：<名录>; 全文在会话存档」
[尾] 当前阶段原文（最近完整上下文）
```

- 中间只放矮 stub 不放长原文——被「去中间」的损耗最小化。
- stub 是合法 user 消息，不伪造 assistant 发言（沿用现有占位语义）；stub 内的命中行是**原文摘录**不是改写。
- tool_use/tool_result 配对闭包保留（不动点扩张，API 契约）。

### 2.6 裁后重估口径（修「usage 锚定失效」）

裁后重估一律**纯字符估算**（estimateTokens 求和 + systemPromptChars/4），不吃旧 assistant 的 usage 锚——usage 锚只在「未裁」判定时用（API 实测最准）。循环内二次评估与 stillOver 判定都用同口径。

## 三、域边界规则：配方默认 + 内容信号动态修正

现状：域推导 = 环境锚定 → 配方 → domain.json recipes 反查（`resolveSessionResearchDomain`），只喂研究记忆过滤。1.2.7 把它升级为**能力边界**：

### 3.1 域判定

- **基线（配方默认）**：现有 `resolveSessionResearchDomain` 不动。
- **动态修正（内容信号）**：扫描最近 N 条（默认 20）消息文本，对每域统计 domain.json `signals` 正则命中数；某域命中 ≥2 且严格多于其他域 → 修正为该域。
- **裁决**：有配方默认且信号不强 → 维持默认；无配方默认（host 现场）且信号强 → 采用信号域；信号打平/无命中 → 维持基线（undefined = 全量，宁多勿缺）。

### 3.2 域能力替换

- **skills 分域注入**（最大收益：~11K → 域内 1-3 篇）：当前域命中 domain.json 的 skills 清单 → 只注入该域 skills + 无域归属的通用 skills（跨域工具型，如 task-alignment / zhishi-cli）；清单里的名字在 skills 目录不存在 → 跳过（容错，whitebox-audit 现状即缺目录）。无域 → 全量（现状）。
- **能力清单分域收窄**：当前域命中 → capabilities 段只列该域 recipes ∪ 绑定环境；无域 → 全量。
- **subagents 按域收窄**（域补丁）：子代理由主 agent 在任务中段派生，任务域在派生时刻已定——可派发清单按 domain.json 的 subagents 收窄（`filterAgentsByDomain`，与 skills 过滤同语义：通用保留、缺目录容错、无域全量）。同一 turn 内域判定一次算出，系统提示与执行栈共用同一 domain。
- **与上下文管理交互**：域标签进分段标注与 stub；系统提示逐 turn 重组（现有机制）天然承载域修正的新鲜性。

## 四、溢出兜底（pi loop 无内建，自研）

- turn 结束（done）带 error → `isContextOverflow`（pi-ai utils，26 条 provider 正则 + 静默溢出 + length 截断）判定；
- 命中 → 置**强制压缩标记**，用同一会话历史重跑该 turn（transform 无视阈值直接压）；**每 turn 最多重试 1 次**（pi 文档建议的 one bounded compact-and-retry）；
- 重试仍溢出 → 走现有 stillOver 语义：明确报错引导 /reset，不再重试。

## 五、不变量（红线）

1. jsonl 全量不动；transformContext 只投影当次视图，不污染 transcript。
2. transform 绝不 throw——任何异常原样透传（丢上下文比炸 loop 安全）。
3. tool 配对闭包不动点保留（API tool_call_id 契约）。
4. stub/占位是合法 user 消息，不伪造 assistant 发言；命中行是原文摘录。
5. 无域信号一律降级全量注入（宁多勿缺）——域过滤是预算优化，不是正确性闸门。
6. 蒸馏弧/研究记忆/专家知识（离线管理）语义不动。

## 八、异常概率与极端情况重估（2026-08-20 复审补录）

按「概率 × 影响 × 当前处理」逐案过一遍；方向性原则：所有降级都向「多留/全量」收敛，且溢出兜底（§四）是窗口口径误差的总接收盘。

| 极端情况 | 概率 | 影响 | 当前处理 | 结论 |
|---|---|---|---|---|
| preset 窗口值高于上游真实值（GLM 5.0/5.1 聚合站 200K 分歧） | 中 | 撞一次 API 400 | 溢出兜底：强制压缩重试一次 → 仍败引导 /reset | 已闭环 |
| preset 窗口值低于真实值（未知模型落 200K） | 低 | 提前压缩、浪费窗口 | 保守方向，不丢数据 | 可接受 |
| provider 不报 usage（聚合平台常见） | 中 | 阈值估算退回 chars/4 纯启发式，可能低估 → 压缩偏晚 | 低估方向由溢出兜底接住；systemPromptChars 补系统提示 | 已闭环 |
| 相位启发式全判错（关键词全不命中/全误命中） | 低 | 粘性继承坍缩 → 几乎无可压段 → 掉第二档截断 | 截断后仍超 → /reset 引导；误判方向是多留非少留 | 可接受 |
| **fuzz 崩溃刷屏**：SIGSEGV 逐条命中存活契约 → key 段膨胀，必保集超阈值 | 中高（fuzz 域常态） | 段级压缩失效，逐条截断后仍可能超 | env_exec 15KB head/tail 截流使单条有界；截断 + /reset 引导 | **已知薄弱**：key 段不做崩溃签名去重，同一签名刷屏全留。记录为后续候选（key 段内按签名去重），本版不动 |
| 图片消息 token 被低估（estimate 固定 4800 字符/张） | 低（本 harness 图片少） | 估算偏低 → 压缩偏晚 | 阈值 0.8 留 20% 余量 + 溢出兜底 | 已闭环 |
| 历史 thinking 块占体积（实测曾 43%） | 中 | 估算把历史 thinking 计入（provider 侧多半不计）→ 估算偏高 → 压缩偏早 | 偏早方向安全；thinking 常规瘦身未做，记录为后续候选 | 可接受 |
| transform 自身异常 | 极低 | 当次不压缩，原样透传 | 可能撞 400 → 溢出兜底接住 | 已闭环 |
| 域信号刷屏误改判（如 pentest `[+]` 在普通输出大量出现） | 低中 | 注入偏窄（非错误） | 改判门槛 ≥3 且 2 倍领先；通用 skills 保留；无信号回基线 | 可接受 |
| 会话中途换模型（窗口变化） | 低 | 阈值按新窗口 | resolution 每 turn 重解析，窗口逐 turn 新鲜 | 已闭环 |
| steering 注入消息被压掉 | 极低 | 纠偏丢失 | 注入消息落在尾段 = 当前阶段 → 必保 | 已闭环 |
| 1M 历史下每 turn 全量分段扫描的 CPU | 必然 | 毫秒级字符串遍历 | 无索引需求，开销可忽略 | 可接受 |
| stub 指针模型无法自助回查存档 | 设计内 | 被压细节模型拿不到 | jsonl 全量存档 + stub 段号指针（现阶段主要告知「压了什么」） | 记录在案，回查工具是后续候选 |

**总评**：真正值得后续立项的只有两条——fuzz 刷屏下的 key 段签名去重、历史 thinking 块瘦身；其余极端情况都有「多留方向 + 溢出兜底」的双保险，无裸 400、无数据丢失路径。

## 九、场景实测结论（2026-08-20，用户指定六场景 + 极端场景 + kimi-for-coding 活体）

测试资产：`src/server/loop/context-manager.scenarios.unit.test.ts`（可重复，进全量套件）+ `tmp/m127-live.mjs`（活体：隔离 sidecar + 播种 228K tok 跨域历史 + K2.7 Coding 真实调用）。**实测抓出并已修四个真缺陷**（见各条）。

### 六场景结论

| 场景 | 结论 | 实测数据 |
|---|---|---|
| S1 web渗透↔代码审计来回切换 | **正确**。域判定跟随最近信号窗口（20 条消息）切换；压缩后两域关键事实均可得（原文或 stub 摘录） | 域轨迹 pentest→whitebox 准确；`session 1 opened`/`CWE-89` 压缩后存活；tool 配对闭合 |
| S2 二进制↔代码审计来回切换 | **正确**。同 S1；崩溃信号与 CWE 跨切换存活 | binary→whitebox 轨迹准确；SIGSEGV/CWE-89 存活 |
| S3 切换中相位不断切换（churn） | **正确**。相位 churn 下布局重排不破坏 tool 配对；anchor 在头、当前阶段在尾 | 相位序列 17 段 5 相位交替，配对闭包校验通过 |
| S4 消息过多、历史在头部 | **初版有缺陷，已修**。实测发现「当前阶段全保」在整会话同相位时必保集=全集，段级压缩空转直接掉第二档截断；且单任务长会话（一个 user 指令 → 上百轮工具调用）段粒度太粗无可 stub。修复：当前阶段全保收窄到最近 8 段（`KEEP_CURRENT_PHASE_SEGMENTS`）+ 段内子段切分（`MAX_SEGMENT_MESSAGES=12`，工具轮边界，配对不拆）+ anchor 相位不被继承 | 修后：300 段 141K tok → 压到 104.9K（阈值 106K），**只 stub 12 段（达标即停不过剩）**，key 事实 30/30 存活 |
| S5 当前数据误判压缩 | **方向安全**。尾段（当前工作）零关键词也永不压缩；中段误判时关键行仍进 stub 摘录；非 key 细节丢失是设计内取舍（jsonl 全量存档可查） | 实测：尾段完整、中段关键行（exit=1/拒绝访问）入 stub、非关键细节丢失可量化 |
| S6 环境与相位误判 → 压缩损失 | **损失有界**。域误判（二进制会话被 CWE 刷屏改成 whitebox）：skills/子代理收窄到错域，但通用 skills 保留；压缩存活契约与域判定解耦，不受影响。方向是「窄」不是「错」 | 误判后 task-alignment 保留、SIGSEGV 压缩后仍可得 |

### 活体（K2.7 Coding 256K 窗口，真实 API）

- **窗口口径**：`contextWindow=262144` 经 runtime 进 loop，实证生效。
- **压缩真实生效**：442,723 tok（校准估算）> 209,715 阈值 → stub 31 段 → 单次调用实报 input 73,756/262,144，一次成功无 400。
- **关键事实全存活**：任务锚（目标 IP）、早期 flag、中期 CWE-787、后期 0xdeadbeef 全部被模型逐条引用（含段号回指，stub 形态可被模型理解）。

### 活体抓出并修复的缺陷

1. **中文估算低估 2.3 倍**（初版 chars/4：估算 226K vs API 实报 521,878，首调直接 400）：新增 CJK 校准估算器（CJK ≈1 tok/字符、其余 ≈2.5 字符/tok，`estimateTextTokens`/`estimateMessageTokens`），阈值判定与裁后重估全换口径；usage 锚的尾部新消息也走校准（pi 的 estimateContextTokens 尾部是 chars/4，不能用）。修后估算 442K vs 实报 521K，残余 15% 由阈值 0.8 余量吸收。
2. **CWE 不在存活契约**（只有 CVE）：被 stub 的白盒段的「CWE-787 at copy.c:118」不进摘录，模型误引 filler 段的 CWE-89。已补 `/CWE-\d+/i`；白盒段整体升级为 key 段。
3. **强制重试预算 0 太暴力**（把 226K 压成 6K 残渣，模型只剩 stub 可读，漏引 0xdeadbeef）：改 `FORCE_COMPACTION_RATIO=0.25`——装得下且保留足够原文。
4. **巨型段空转**（见 S4 条）。

### 极端场景

| 场景 | 结论 |
|---|---|
| E1 fuzz 崩溃刷屏（全 key） | 不 stub（契约如此）→ 第二档截断压到阈值内（24K→14.5K），不炸、配对闭合、无 stillOver |
| E2 单巨型段（500KB 单条） | 段级不可拆 → 截断兜底，不炸 |
| E3 单段会话 | 无可压，anchor 原样存活 |
| E4 无 user 退化输入 | 整体一段，正常产出 |
| E5 1M 级历史性能 | 800 子段 ~80 万 tok：切分+压缩 41ms，无 O(n²) |

### 已知边界（记录在案）

- **域切换有迟滞**：信号窗口 = 最近 20 条消息，切域需新域信号在窗口内占优（防单条翻转的滞后设计）；实测切回渗透 2 条消息时仍判 whitebox。
- **模型对 stub 的阅读不是 100%**：极限压碎（ratio 0）下曾漏引一条全文中的事实（0xdeadbeef 在视图中但未被引用）；0.25 预算的活体 run 4/4 全引用。
- **key 段不做崩溃签名去重**：fuzz 刷屏时全 key 段全留，靠截断兜底（E1 实证可工作，但上下文质量依赖截断）；签名去重是后续候选。
