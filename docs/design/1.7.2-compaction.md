## 2. 调研结论（对应三篇材料 + 实现级参考）

**论文/文章层**：
1. **HL-Mem（2026-09-11）**：记忆 = 受治理的认知系统。Event（不可变原始事件，证据追溯）+ Claim（可更新结构化事实，动态修正）；区分有效时间与记录时间；**后台异步 Worker** 做去重/冲突消解/生命周期；本地 SQLite 单文件。
2. **2025 综述三维框架**：压缩问题本质是 Dynamics 的「形成/演化/检索」问题——**「记忆形成」与「上下文窗口管理」是两个正交机制**，绑定在一起（裁剪即压缩、压缩即丢）是错误架构。
3. **MemGPT**：上下文窗口是工作集；历史是数据，按需移入移出。**置换不是压缩，不做语义改写**。
4. **Zep/Mem0**：事实随时间演化（增/改/删 + 冲突检测标记失效）——Claim 演化是记忆系统核心操作，zhishi 的 archive 纠正语义已覆盖（1.4.4），缺的是**形成**（谁来写）与**遗忘**（何时淡出）。

**实现层（源码级考察，2026-09-12）**：

| 实现 | 语言/许可 | 对 zhishi 的用途 |
|---|---|---|
| [HL-Mem](https://github.com/lohr13/hl_mem)（v1.1.7） | Python / Apache-2.0 / SQLite-first | **写管线蓝本**（见下）；提供 REST/MCP 接口，可作 sidecar 服务集成（路线图） |
| [@mastra/memory](https://github.com/mastra-ai/mastra/tree/main/packages/memory) | **TypeScript** | 与 zhishi 同栈；observational-memory 的 `async-buffer` 策略 / `activation-ttl` / `extraction-runner` / `built-in-extractors` 是异步提取+衰减的 TS 实现参考 |
| [getzep/graphiti](https://github.com/getzep/graphiti)（Zep 核心） | Python / Apache-2.0 | 时序知识图谱（边失效 = 事实随时间演化）——设计参考；zhishi archive 已覆盖纠正语义，不引入图引擎 |
| [mem0](https://github.com/mem0ai/mem0) + OpenMemory MCP | Python 核心 + TS SDK | Claim 增/改/删 + 冲突检测操作语义参考 |
| Letta | Python | memory blocks + sleep-time compute——架构参考 |

**HL-Mem 写管线（可直接映射到 zhishi 的实现细节）**：
```
幂等 Event 摄入 → 批量租约窗口（max 4 events / max 2s，无 idle timer）
→ 七字段 LLM 提取 → 确定性 JSON 修复 → AdmissionPolicy 纯校验（notability/证据/秘密值）
→ fact_hash 精确去重 → conflict_key 确定性冲突消解 → LLM 四路灰区冲突收敛
→ 近重复复用（结构+词法+余弦+保护原子）→ 0.82 语义候选 → 单事务提交（BEGIN IMMEDIATE）
```
配套：双时间模型（valid_from/to + recorded_from/to）、TTL/衰减/遗忘、审计账本、
Context Packet = token-budgeted 交付投影（携带证据 + answerability：no_evidence 硬拒答 / low_confidence 软拒答）。

**开源库可用性结论**：无「即插即用」的 Node 库能直接替换 zhishi 记忆层（archive 研究语义 / recall 工具 / jsonl 会话线深度耦合；Mastra memory 绑定 Mastra agent 框架；HL-Mem 是 Python 服务）。两条路：
- **设计蓝本（1.7.2 采用）**：HL-Mem 写管线 + Mastra 异步缓冲实现细节 → Node 复刻「会话级 Claim 治理」；
- **服务集成（路线图）**：HL-Mem 以 MCP/REST sidecar 形态挂进 zhishi，增强跨会话长期记忆。

## 3. 架构定案：Event/Claim 双通道 + 程序化置换 + 程序化治理

```
工作记忆（每轮上下文，预算有界）
  = 系统提示 + Claim 层(archive 全量) + Event 索引(session-claims 条目)
    + 最近窗口原文(预算内动态算) + recall 指针

置换（程序决定，token 预算触发，纯函数，零 LLM 调用）：
  最老消息按段原子移出工作记忆 → Event 原文永远在 jsonl（不可变证据）
  → 上下文留「行区间指针 + 索引条目」；零摘录、零供应商假设、信息结构性不丢

Claim 治理（程序保证，双保险）：
  ① 交互检查点（形成）：把 auto-run 的 4 轮检查点抽到共享层，交互会话每 N 轮注入；
     置换动作前强制一轮「整理研究状态」
  ② 异步 Worker（兜底固化）：空闲/定时后台任务从 Event 层增量提取/更新 Claim
     （archive 实体 + research_log 事件 + session-claims 文件），去重、冲突消解——
     复用蒸馏弧调度基建，当前会话模型，异步不阻塞轮边界
```

## 4. 技术方案（逐模块）

### M1 工作记忆窗口置换（核心）

**替换对象**：`makeCompactionTransform`（compaction.ts）的 stub/truncate 路径在**交互会话**改为窗口置换；auto-run 线同策略（auto-run 上下文同样受益）。旧段级压缩保留为兼容路径（子 loop/无 recall 场景可继续用），不删。

**参数**（导出常量，可调）：
- `WORKING_MEMORY_TARGET_RATIO = 0.25`：置换目标 = 0.25 × contextWindow（1M → 250k 估算）；
- 触发阈值沿用 `DEFAULT_THRESHOLD_RATIO = 0.8`（不提前置换）；
- `KEEP_RECENT_USER_MESSAGES = 20`：工作记忆内 user 消息原文保留上限（超出的最老 user 消息随段移出——原文在 jsonl，Claim 侧由异步 Worker 提取「用户指令历史」）。

**置换粒度**：段原子（复用 `segmentContext` 的 tool_use/tool_result 配对闭包——不拆对）。

**工作记忆组装**（新纯函数 `buildWorkingMemory`）：
```
[系统提示] + [archive 全量] + [session-claims 索引(如有)] + [最近窗口原文]
+ [被移出段的指针块：段#N phase 行区间 x-y + session-claims K#n 引用]
```
指针块复用 `buildPointerCard` 形态（行区间 + recall 用法），但**不再需要 harvest 摘录**——指针只做寻址，语义在 Claim 层。

**Event 索引数据源决策**：`research_events` 表**无会话键**（只有 workspace），不能按会话查询。因此会话级索引落在**新文件** `loop-sessions/<id>.claims.json`（异步 Worker 维护：数组条目 `{kind: fact|decision|dead-end|todo, text, evidenceRefs(E#N/行区间), updatedAt}`）——即 HL-Mem 的 Claim 快照。工作记忆注入的是这个文件的条目清单（每条约一行）。

### M2 Claim 治理

**M2a 交互检查点（形成）**：
- `ARCHIVE_CHECKPOINT_INTERVAL/ARCHIVE_CHECKPOINT_TEXT` 从 auto-run.ts 抽到共享模块（如 `src/server/loop/archive-discipline.ts`）；
- 交互轮注入点：`assemblePiSystemPrompt` 的 append（与 mission 同级）——按轮数确定性注入「整理研究状态 + 写 research_log + 更新 session-claims」提示；
- **置换前强制检查点**：窗口置换发生前的那个 turn，注入「本轮结束前整理研究状态」——程序决定时机，模型执行整理；不执行也照常置换（信息不丢，只是索引薄）。

**M2b 异步 Worker（兜底固化，HL-Mem 写管线蓝本）**：
- 新后台任务类型（对齐蒸馏弧：Rust TaskScheduler 定时触发 + sidecar 执行），管线逐段映射 HL-Mem：
  1. **幂等事件摄入**：治理游标 = jsonl 行位点（增量读自上次位点起的新消息）；
  2. **批量租约窗口**：单次治理窗口 ≤ N 条新消息（常量，如 8），无 idle timer（对齐 HL-Mem「count + max wait 两控」——zhishi 侧用定时扫描替代 wait）；
  3. **LLM 提取**：当前会话模型，结构化输出 = archive 实体（假设/证据/结论/问题）+ research_log 事件（补写遗漏产出）+ session-claims 条目（fact/decision/dead-end/todo）；
  4. **纯校验（AdmissionPolicy）**：notability/证据行位点/空值/秘密值——确定性规则，提取失败不落库；
  5. **去重与冲突**：`computeContentHash` 精确去重（已有）→ conflict_key 确定性合并 → 灰区冲突 LLM 收敛（四路：覆盖/合并/并存/忽略）→ 近重复复用（同 subject 相似条目更新而非新增）；
  6. **单事务提交**：archive/research_log/session-claims 各自落库沿用既有锁与原子写纪律；
  7. **审计**：每次治理写一条治理记录（位点/提取条数/去重数/冲突裁决/错误）——可解释、可回溯。
- 模型：会话当前模型（读 session meta）；失败静默，下轮从同一位点重试；
- 触发：每 30 分钟扫描一次活跃会话（蒸馏弧同调度形态），间隔走常量。

### M3 看门狗分层

`runLoop`（loop.ts:198）静默看门狗两段计时：
- 收到任意事件前：`MODEL_FIRST_EVENT_TIMEOUT_MS = 300_000`（prefill 预算，可注入）；
- 收到任意事件后：`MODEL_SILENCE_TIMEOUT_MS = 90_000`（流间挂起检测，现状）；
- 工具执行期不计时（现状）；错误文案区分「prefill 慢」与「流间挂起」。

### M4 收割侧车写入性能（可选，顺带）

`appendHarvestEntries` 改锁内纯追加 + `K#ulid` 编号（不再读全量求 maxSeq 重写 247MB）；读侧按需查找 + 进程内缓存。M1 上线后 harvest 摘录职责大幅缩减，此项可延后。

## 7. 实现级技术方案（v6，基于源码逐点核对）

> 以下每个落点都对照过当前实现：archive.ts 的实体 CRUD 与锁纪律、session.ts 的
> meta/追加语义、recall.ts 的取回面、cron/routes.ts 的蒸馏弧执行形态、
> chat-engine.ts 的 transformContext 装配点（1272-1335）。

### 7.1 工作记忆窗口置换（M1，全局）

**新模块 `src/server/loop/window-transform.ts`**（纯函数）：

```
buildWorkingWindow(messages, { budget, keepRecentUser, sessionId })
  → { llmMessages, pointers, evictedRange }
```

- 从最新消息起按**段原子**（复用 `segmentContext` 的 tool 配对闭包）向前累积，
  估算 tokens ≤ `WORKING_MEMORY_BUDGET_RATIO × contextWindow`（0.25 × 1M = 250k）即停；
- kept 范围内 user 消息数 > `KEEP_RECENT_USER_MESSAGES`（20）→ 继续向前整段移出直到达标；
- 被移出部分 → 每段一个**目录指针块**（纯函数组装）：`[段#i phase 已沉淀] 行区间 x-y ·
  关键行命中（复用 keyHits 提取，仅作目录提示）· 工具名 · recall({lines:"x-y"})`——
  语义不在指针里，在 Claim 层；
- `llmMessages = [指针块...] + kept 尾段`；jsonl 全量不动（既有纪律）。

**全局接线与旧路径退役**：
- 两处装配点（chat-engine.ts:1282 交互 / 1622 invokePiSession）**全部**替换为窗口置换；
- 子 loop 的 recall 工具**全量注册**（补齐既有「子 loop 无 recall」场景——指针块的取回
  指引在所有线成立；A2-3 的 hasRecall 分形态随之废弃）；
- 旧段级压缩（compaction.ts 的 stub/truncate 主路径 + FORCE_COMPACTION_RATIO 兜底）**退役删除**，
  `isContextOverflow` 重试逻辑保留（溢出兜底改为「窗口预算再收紧一次重跑」）；
- 1.2.7 的 `selectSegmentsToStub/applySegmentStubs/buildSegmentStub` 等仅被旧路径消费的函数
  一并删除；`segmentContext`/`keyHits`/`estimateMessagesTokens` 保留（窗口置换与指针块继续用）。

### 7.2 Claim 治理（M2，HL-Mem 管线映射 + zhishi 现有函数复用）

**游标**：`LoopSessionMeta` 增加 `claimsCursor`（已治理消息下标，缺省 0；消息 i ↔ jsonl 行 i+2——
行区间语义与 recall 完全同口径）。

**治理管线 `src/server/loop/claim-governance.ts`**（新，fake LLM 可注入）：

```
① 幂等摄入：loadLoopSession → 自 claimsCursor 起取 ≤GOVERNANCE_WINDOW(8) 条新消息
② LLM 提取：会话 meta 的 model/providerId → 结构化输出三类：
   archive 实体（H/V/C/Q + refs）｜research_log 补录（workspace 级）｜
   session-claims 条目（fact/decision/dead-end/todo + 行区间证据）
③ 纯校验（AdmissionPolicy）：非空/证据行位点在窗口内/无秘密值——不通过不落库
④ 去重与冲突：
   - archive/research_log：computeContentHash 精确去重（已有函数）
   - session-claims：conflict_key（kind+subject）确定性合并 → 灰区 LLM 四路收敛
   - archive 冲突走既有 correctEntity 语义（人纠正 > 模型，权威序不变）
⑤ 落库：addHypothesis/addEvidence/addFinding/addQuestion/correctEntity（archive 既有
   锁内读-改-写 + tmp+rename）｜writeResearchEvent（store 既有）｜session-claims 文件
   （同 harvest 的文件纪律）——各自原子，顺序为 claims → archive → events → cursor 推进
⑥ 审计：治理记录（游标/提取条数/去重数/冲突裁决/错误）追加进 session-claims 文件
```

**调度**：sidecar 受护定时器（`claim-governance-arc.ts`）——每 `GOVERNANCE_INTERVAL_MINUTES=30`
分钟扫描活跃会话线（sessions.json 近 7 天 + 有 loopSessionId），逐线跑治理管线。
与 Rust TaskScheduler 解耦（治理是引擎内务,不需要 UI 可见性/人工编辑;蒸馏弧那种
用户可感知的任务形态不适用）；定时器随 sidecar 生命周期重启即恢复,游标幂等,
多 sidecar 并发由 claims 文件锁 + 游标 max() + 内容去重兜底。

**检查点（形成侧）**：`ARCHIVE_CHECKPOINT_INTERVAL/TEXT` 抽共享模块
`src/server/loop/archive-discipline.ts`；交互轮在 `assemblePiSystemPrompt` 的 append 注入
（轮数 = 会话 user 消息计数，纯函数判定）；window transform 触发置换的那一轮额外注入
「本轮结束前整理研究状态」。auto-run 沿用既有 4 轮检查点（引用共享模块）。

### 7.3 看门狗分层（M3）

`loop.ts:198` 静默看门狗两段计时：收到任意事件前 `MODEL_FIRST_EVENT_TIMEOUT_MS = 300_000`
（prefill 预算）；收到后 `MODEL_SILENCE_TIMEOUT_MS = 90_000`（流间挂起）；工具执行期不计时（现状）。
错误文案区分「prefill 慢（上下文较大）」与「流间挂起」。

### 7.4 时间解释（M4，bitemporal）

- `ArchiveEntity` 与 session-claims 条目增加 `validFrom/validTo`（事实有效时间，可空 = 无限/
  未知）——`createdAt/updatedAt` 即记录时间（已有），双时间模型齐备；
- 治理管线 LLM 提取时输出时间锚（「何时为真」）；archive 实体带时间窗后：
  - `renderArchiveForInjection` 对已失效实体（validTo < now）标 `[已过期]` 而非删除；
  - 结论引用过期证据时提示（finding refs 指向 validTo 已过的 V#N）；
- 报告导出/档案投影同口径展示时间窗。

### 7.5 遗忘与生命周期（M5）

- session-claims 条目增加 `salience`（LLM 提取时评分 0-1）与 `lastTouchedAt`；
- 治理管线内的生命周期维护：
  - **衰减**：salience 按时间衰减（半衰期常量，如 30 天）；
  - **归档**：salience < 阈值（如 0.15）的条目移出工作记忆注入、保留在文件（可查）；
  - **遗忘**：`zhishi claim forget <id>`（CLI）与治理任务的 TTL 到期删除（双保险：人可
    主动遗忘，程序按 TTL 清理；删除前记审计行）；
- archive 实体不做自动遗忘（研究档案是审计资产），过期标记走 M4 的 validTo 语义。

### 7.6 自动检索注入（M6）

- 工作记忆组装时（buildWorkingWindow），以当前轮内容（最新 user 消息 + 最近工具结果）为
  查询，对 session-claims + archive 做**关键词/前缀检索**（无新依赖；claims 文件量小，
  进程内索引即可），命中条目注入工作记忆（预算内，≤ 注入上限如 8 条）——模型无需手动
  recall 即可获得相关历史；
- 检索顺序：session-claims（本会话 Claim）→ archive 实体 → harvest 关键行；
- 注入条目带来源标注（claim id / 行区间），与手动 recall 互补（recall 工具保留）；
- 选型说明：第一版用关键词检索（claims 提取时由 LLM 同时产出 `searchTerms` 字段——
  检索词随记忆条目一起落盘，避开中文分词问题）；embedding 检索留作后续增强（需要
  向量服务，属技术选型优化而非功能缺口）。

### 7.7 收割侧车收口（M7）

- `appendHarvestEntries` 改**锁内纯追加**（`K#ulid` 编号，不再读全量求 maxSeq 重写 247MB）；
- 读侧：`readHarvestEntry` 按需查找 + 进程内缓存（追加时同锁更新缓存）；
- **GC**：治理任务附带收割物生命周期维护——`harvestEntries` 全部被治理（claimsCursor 已
  覆盖且行区间已被 claim 引用）的条目，按保留策略（如超过 60 天或已被治理）**归档压缩**
  （保留条目元数据 + 行区间引用，删除已进 Claim 的重复正文）——侧车不再只增不减；
- `recall({ref})` 与 `recall({lines})` 语义不变（ref 取回可能命中「已归档」提示 → 引导
  lines 取回原文）。
