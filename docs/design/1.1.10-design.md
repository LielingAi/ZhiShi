## A′ 子代理 transcript 只读查看

**方案论证（已敲定）**：1.1.9 U1 核实发现「切过去」无目标——子 loop 会话
未持久化、无 sessionId 映射。「完整进入/续跑子会话」需一整套导航语义
（主线让位/回退栈/嵌套/续跑歧义），低频审计场景不值；只读查看吃下
「结论可审计」（证据链/幻觉核查）的核心价值。

**已核实的链路事实**：

- `spawnSubLoop` 支持 `storeDir` 持久化（`subagent.ts:127-134`，
  appendLoopMessages 独立 jsonl，与主会话平级）——但生产路径
  `chat-engine.ts:751` 的 `createDelegateTaskTool` **没传 storeDir**。
- `DelegateTaskNotifier.finished`（`subagent.ts:166`）签名无 sessionId，
  但调用点（`:247`）手里有 `result.sessionId`；广播在
  `chat-engine.ts:761-770`（`chat:subagent-finished`）。
- 子 loop 事件已有透传：`chat:subagent-tool-use/result-complete`（带
  subagentId=taskId）。
- TUI 侧：`event-reducer.ts` 把 subagent-finished 折进
  `SessionState.tasks`（summary/status/done）；`/tasks` 面板（1.1.9）
  详情页目前只显示 summary 全文。

**改动**：

1. 服务端：
   - `chat-engine.ts:751` 给 `createDelegateTaskTool` 传 `storeDir`
     （loop-sessions 默认目录，与主会话同一个——loadLoopSession 可读回）。
   - `DelegateTaskNotifier.finished` 加 `sessionId` 参数；广播
     `chat:subagent-finished` 带 `loopSessionId`。
   - 新增读取端点（admin-api 或普通路由，看哪边更顺）：按 loopSessionId
     返回 loop-sessions 的消息序列（结构化：role/工具调用/结果/文本），
     供 TUI 拉取。注意大小截断策略（transcript 可能很长——先全量，
     超阈值截断并标注）。
2. TUI：
   - reducer 把 `loopSessionId` 存进 tasks 记录。
   - `/tasks` 详情页：有 loopSessionId 的任务 → 拉 transcript 展示
     （每轮：工具调用卡摘要 + 输出 + 助手文本），详情页支持滚动
     （复用 drawer 的 offset 滚动模式）。拉取失败/无 sessionId（旧任务）
     → 退回只显示 summary。
3. 验收：真跑一个 delegate_task 子任务 → /tasks 里看完整工作史。

## B app.ts 拆分（纯搬移）

照 1.1.7 手法，铁律相同：函数体逐字搬、既有测试断言零改动、每块抽完全量绿。
app.ts 现 ~1790 行、60+ 方法。切分（按依赖内聚度）：

1. **slash 命令** → `slash/`：每条命令一个 handler（接收 client + 上下文
   回调）；/model /mcp 子流程各自成文件。
2. **overlay** → reducer 模式：`model.ts` 的 `reduceHiddenLine` 是现成
   范式；7 种 overlay（completion/help/drawer/rewind/history-search/modal/
   tasks）的状态变更收纯函数。
3. **gate + manualForm** → `gate-controller.ts`（正门选择 + 手动 SSH 表单，
   app.ts:194-399 一带）。
4. app.ts 只留：按键路由 + SSE 泵 + 渲染编排组装。目标 ≤600 行（软目标，
   不为压行数发明抽象）。

风险点：app 级测试只有 3 个文件（attach/gate-reentry/ux-1-1-9/tasks-overlay），
大部分逻辑靠类型与全量回归兜底——每刀后必须全量 `npm test` 绿。
