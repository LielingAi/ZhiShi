# 1.2.3 分析记录：#5 修复 + 构建产物验证

> 2026-08-22。本版分两半：修 issue #5（含根因链审查）+ 建产物级验证。
> 本文档先记录分析，方案待与用户对齐后补「定稿」节。

## 一、#5 根因链（esbuild metafile 实测）

CLI bundle（`src/cli/zhishi.ts`，cjs）里卷进了 `src/server/utils/runtime.ts`
的 `getScriptDir()`；cjs 无 `import.meta` → 运行时 fallback 到 cwd 并
`console.warn` → 日志被 TUI 渲染在输入框上方。

**引用链（三条，metafile 实测）**：

1. `cli/zhishi.ts` → `cli/expert-edit.ts`（1.2.1 引入：CLI 侧校验直接调服务端
   `validateEntry`）→ `server/expert/validate.ts` → `server/memory/store.ts`
   → `server/utils/runtime.ts`
2. `cli/zhishi.ts` → `server/memory/store.ts`（直接用 `RESEARCH_TASK_KINDS`
   常量）→ `runtime.ts`
3. TUI 内：`event-reducer.ts` → `blocks/signal-extract.ts` →
   `server/domains/manifest.ts` → `runtime.ts`

**比日志更深的问题**：fallback 到 cwd 拿到的目录是**错的**——CLI 下任何
合法的宿主资源定位（如 skills 目录）都会落到错误路径。日志只是烟雾，
路径错误才是火。

**编译期早有信号**：esbuild 警告 "You need to set the output format to esm
for import.meta to work correctly" 一直存在，无人处理——构建警告零容忍的
缺失是本版要补的制度。

## 二、修复方案候选（待对齐）

- **A. CLI bundle 改 ESM**（`esbuild-bundle.mjs` format: 'esm'）：治本——
  repo 本身 type:module、server bundle 已是 esm，CLI 的 cjs 是历史异类。
  要动：`zhishi.cmd`、resources/cli/package.json（type 标记）、Rust
  `cmd_sync_cli` 的读取路径、banner 的 createRequire 互操作（server 已有
  先例）。风险：bundle 内若有 require 依赖需实测。
- **B. 切断 CLI→server 运行时依赖**（架构正解）：`RESEARCH_TASK_KINDS` 挪
  shared/；CLI 校验不引服务端 validate（或 validate 挪 shared）；
  signal-extract 不引 domains/manifest。降爆炸半径，顺带还分层债。
  但单独不够——CLI 若合法需要资源定位（skills 目录），cjs 下仍 fallback。
- **C. getScriptDir 静默 + argv[1] 兜底**：最小修复，治标。

**倾向：A 为主（治本 + 路径正确），B 顺带做掉常量/校验的分层（CLI 不该
为两个常量拖进 server 运行时）。C 不做。**
